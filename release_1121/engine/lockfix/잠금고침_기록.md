# 사운드 화면 1~2초 멈춤 — 엔진 잠금 교착과 DLL 고침 (2026-11-24, 세션 「길티 크라운 사운드 모드 성능」)

사용자 「길티 크라운 사운드 모드를 만들었는데 너무 느려. 원인을 조사하고 개선해줘」(같은 날 06:47 다른 세션에는 「사운드 모드 반응이 굉장히 느린데?」).
대본 쪽 고침(풀이·막대를 한 프로세스로, 올림 때 Delete 없이 Fade 만)은 세션 「길티 크라운 최종 패치 검토」가 했다(nss c30df6fb, 07:35 놀이 사본 설치).
이 폴더는 엔진(DLL) 쪽 근본 고침이다.

## 원인 (EXE 정적 분석 + 숨긴 시험)
- 대본의 CreateProcess 프로세스는 실제 OS 스레드다(스레드 만들기 0x48d380, 스레드 함수 0x473650). 대본 스레드들과 렌더 스레드(0x44ce90)는
  전역 뮤텍스 M([0x6212b4]; 잠금 0x44abc0 = WaitForSingleObject(M,1000) 뒤 시간 초과면 무한 대기, 풀기 0x44ac00)으로 번갈아 돈다.
- `PassageTime()`·`RemainTime()`: VM(0x43b2bb, 0x43af10)이 M 을 잠근 뒤 0x44c4c0 을 부른다. 0x44c4c0 은 지우기 잠금 E(수동 이벤트 [0x54ed04])가
  잡혀 있으면 **M 을 쥔 채** `WaitForSingleObject(E,1000)`, 시간 초과면 0 을 돌려준다(PassageTime = 길이 − 남은 시간이라 그 틱엔 곡 길이로 튄다).
  DurationTime(0x44c6f0)은 기다리지 않는다.
- `Delete()`(0x40e310 → 0x449e50): M 없이 들어와 [0x54ed08]·**E 를 먼저 잡고**(ResetEvent 0x449ef3) 그다음 M 을 잠근다(0x449f37). 끝에 SetEvent·ReleaseMutex.
  개체 종류와 무관하다(색·그림·글).
- 그래서 한 대본 스레드가 Delete 로 E 를 잡고 M 을 기다리는 사이 다른 대본 스레드가 M 을 잡고 PassageTime 을 부르면, 서로의 잠금을 기다리다
  1000ms 시간 초과로만 풀린다. 렌더 스레드는 프레임마다 M 이 필요하므로 그동안 화면이 선다. 기다리던 스레드가 둘(막대 + 가사)이면 2초.
- 사운드 화면: 막대 프로세스가 16ms 마다 PassageTime, 가사 프로세스(kr_lyrics.nss KrLyTick)가 100ms 마다 PassageTime+RemainTime,
  풀이 프로세스가 줄을 옮길 때마다 Delete(06:37 설치판 302254aa) → 곡이 나오는 동안 커서를 움직이면 계속 걸렸다.
- 본편도 같은 짝이 있다: 가사가 나오는 곡 동안 가사 프로세스 ↔ 본 대본의 Delete.

## 고침 (src\script_locks.inc)
- 0x44c4c0 첫머리 갈고리(hookRemainTime, native_hook_manifest.h 한 줄): E 가 잡혀 있으면 M 을 놓고(0x44ac00) E 를 기다린 뒤 M 을 다시 잡고(0x44abc0)
  원래 함수로 — Delete 와 같은 순서가 된다. 엔진 안의 1000ms 대기(0x44c4ff `push 1000`)는 0 으로 바꿔 M 을 쥔 채 E 를 기다리는 일이 아예 없게 하고,
  그 사이 E 가 잡혀 엔진이 읽지 않고 0 을 돌려준 경우(그 Delete 는 M 없이는 못 끝나므로 E 가 계속 잡혀 보인다)는 다시 돈다. 합쳐 1초를 넘기면 엔진처럼 0.
- (v3.1, 아래 「둘째 고리」) 대본 스레드 함수 0x473650 갈고리로 스레드마다 자기 문맥을 TLS 에 적어 두고, 멈춤 요청([ctx+4]==0)을 받은 스레드가
  E·[0x54ed08] 을 기다리는 채 30ms 가 지나면 자기 프레임을 멈춤으로 표시(소멸자 둘째 단계 0x45ae79 와 같은 일)하고 그 명령에서 돌아간다.
  Delete(0x449e50) 첫머리 갈고리는 두 잠금을 5ms 조각으로 대신 기다렸다가(최대 1.5초) 엔진 함수로 넘긴다. 멈춤 요청이 없는 스레드는 달라지는 것이 없다.
  30ms 는 원작의 Request(프로세스, Stop)(부른 함수들이 돌아올 때까지는 계속 돎)을 지키려는 것 — 무관한 Delete 가 잠깐 쥔 잠금 때문에 끊기지 않게.
- 시험 스위치(N2HD_PROFILE_DIR 있을 때만): `N2HD_TEST_LOCKFIX_OFF=1` = 엔진 그대로, `N2HD_TEST_LOCKFIX_NOSTOP=1` = 멈춤 요청 부분만 끔.
  locks.log: `stepped-aside`(비켜 줌)·`gave-up`(1초 넘김)·`stop-asked`/`delete-stopped`(지워지던 스레드가 빠져나옴)·`delete-waited`·끔일 때 `engine-waited`.
- 이 폴더의 src 는 「engine\src(ac07b4a7 시점) + 코덱스 lyric_save_view.inc(놀이 사본 DLL 54196c77 과 같은 세 군데 치환, merge_codex_lyric_view.py)
  + script_locks.inc」. 빌드 build_lockfix.cmd → out\n2hd_runtime.dll. 공용 소스에 들이기 apply_to_src.py.

## 둘째 고리: 돌고 있는 프로세스를 Delete 로 지울 때 (3.1초)
- 스레드를 가진 개체의 소멸자(0x45ad80): 상태 [ctx+4]=0, 깨움, WaitForSingleObject(스레드,100) → 안 끝나면 자식 문맥도 0 으로 놓고 1500 → 0x48d8b0 → 1500 → TerminateThread.
  VM(0x4737f0)은 문장 사이에서 [ctx+4] 를 보므로, 스레드는 지금 하던 명령이 끝나야 멈춘다.
- 지우는 쪽(Delete("ku_l*"))은 [0x54ed08]·E 를 쥔 채 기다린다. 지워지는 프로세스가 그때 자기 Delete(막대 A/B) 안이면 같은 잠금을 1500ms×2 기다려
  서로 물린다 → 100+1500+1500 뒤 강제 종료. PassageTime 이 E 때문에 0 을 주면 위치가 곡 길이로 튀어 그 틱에 Create+Delete 가 꼭 생긴다.
- 고침: (대본, 다른 세션 몫) 프로세스에 끝내라고 하고($KUH_ON=false) 고리가 끝난 것을 확인한 뒤 KuClear. (DLL v2) 멈춤 요청을 받은 스레드는
  0x44c4c0 에서 E 를 기다리지 않고 바로 돌아간다 — 스레드 문맥은 스레드 함수 0x473650 갈고리가 TLS 에 적어 둔다. 가사 프로세스처럼 시간만 읽는
  프로세스가 지워질 때의 1초를 없앤다(자기 Delete 안에 있던 경우는 대본 쪽 고침이 필요).
